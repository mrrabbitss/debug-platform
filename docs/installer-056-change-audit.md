# 0.5.4 / 0.5.5 服务器安装失败变更审计

审计日期：2026-09-10。历史归因依据是 Git 历史及四份经脱敏读取的公司安装日志。本文不保留日志原文、真实目录、Windows 账号、令牌或其他公司信息；以下日志以 `L-1` 至 `L-4` 匿名标识。历史审计本身只读，另行执行的 0.5.6 新安装验收见 VALIDATION.md；没有重复旧功能回归或手动 CI，也不将本机验证视为公司服务器验收。

## 结论

两版失败的代码触发点已经可以确定：安装器在同一父目录中对应用目录执行重命名时被 Windows 拒绝。根目录替换设计最早出现于 `b9ae846`（2026-09-03）的通用离线安装器，而不是 0.5.3；服务器 EXE 在 `74a3a04`（2026-09-08）开始调用该发布器。`30b6f3b` 将该流程中的 `Move-Item` 换成 `Directory.Move`，`01327e4` 又为同一重命名增加有限重试。`a82015e` 的六文件导入是知识库升级流程，和目录发布失败没有因果关系。

日志能够证明调用被拒绝，不能证明哪个进程、驱动或安全策略持有/拒绝了目录。尤其不能把错误 32 自动归因为服务器进程，也不能把错误 5 自动归因为某个安全软件；日志没有进程名、句柄追踪或安全事件。

## 每项变更是否必要

### 根目录替换与 `30b6f3b`

**必要性：防止旧程序部分移动是必要的保护目标；采用整目录改名只是可选实现，并非用户要求，也不是唯一实现。对公司服务器的错误 5/32 不是根因修复。** `30b6f3b` 的定向故障测试针对 `Move-Item` 的逐项移动语义；改为 `Directory.Move` 能保留完整旧树，但没有消除对目录重命名的依赖。

代价是根替换仍必须先执行 `destination → backup`，后执行 `staging → destination`。这两个调用正是 `L-1` 至 `L-4` 所在阶段。因此它消除了部分移动损坏，不能消除 Windows 对目录重命名的拒绝。

### `a82015e` 的六文件导入

**必要性：只在“旧知识库既要完全保留，又要补入六文件”的额外约束下才必要；不是安装失败修复。** 用户明确需求是安装后必须内置六个 Skill。代码中，空知识库的安装默认初始化早已由 `7c659b5:backend/app/services/knowledge_reset.py:370-384` 限定为仅空库可执行；`a82015e` 才为已有库增加 `preserve_existing=True` 的人工确认入口。

“已有库一律显示/处理为 PRESERVED，再由管理员或专家点击导入”是我们的数据保护策略推断，并非用户明确要求。其代码表现为：预览将已存在、草稿或同名文件标记为冲突；仅六项均为 `ADD` 才允许确认；确认后不 retire 旧文档，并把现有活跃分块加入新索引代际。见 `a82015e:backend/app/services/knowledge_bundle_import.py:32-49,67-75` 和 `backend/app/services/knowledge_reset.py:377-378,601-603,730-744`。

该入口也不是诊断 Chat 的“AI 自动导入”：它要求 `confirmed: true`，把操作和后台索引任务持久化；仅当所用 Embedding 配置需要外发且未获许可时阻止索引。见 `a82015e:backend/app/api/bundled_skill.py:43-65`、`backend/app/services/knowledge_reset.py:720-744`。所以它增加了实现与操作步骤，却没有降低目录发布失败的概率。

### `01327e4` 的重试

**必要性：可作为短暂 Windows 拒绝的有限韧性措施，但不是必要的根因修复。** 它不合并目录、不杀进程、不改权限，也不突破 15 秒；这保留了安全边界。`L-2` 至 `L-4` 的 31 次失败说明，面对本次持续性拒绝，重试只让失败更可诊断，未恢复安装成功。

## 消除根目录替换后的保护边界

0.5.6 已实现：服务器安装只向唯一版本目录直接落盘、完成校验，不移动旧 `app` 或新 staging；随后自动调用六文件更新。首次空实例随第一次启动自动入库。具体安装验收状态见 VALIDATION.md，以下是设计边界。

| 边界 | 去除根目录替换后可消除 | 仍必须明确保留 |
| --- | --- | --- |
| Windows 错误 5/32 的触发面 | 删除 `destination → backup` 与 `staging → destination` 两个目录重命名调用，因而消除本次已证实的触发点。 | 直接写入版本目录仍可能被拒绝；这不证明 OS 级权限/句柄问题已消失。 |
| 旧版可用性 | 不再为发布新版本改名或回滚旧应用树，旧版本目录应保持原状。 | 启动器/版本选择切换必须在新目录完整校验后进行，并在切换失败时继续指向已验证旧版。 |
| 新版完整性 | 版本目录先完整写入并核验，再成为可启动版本。 | 保留包哈希、文件清单、隔离自检；更新知识仅使用所选 Embedding，不调用诊断 Chat/CLI。 |
| 六文件交付 | 自动调用六文件更新，能直接满足“安装后内置六 Skill”的明确需求，而不再把成功依赖于人工再点击导入。 | 必须把“更新”对已有同名文件、人工修改、草稿、案例、报告、模板和索引代际的规则写清楚；自动化不能隐含授权覆盖用户知识。 |
| 数据与恢复 | 应用版本与业务数据继续隔离，应用写入失败不应改动数据库或业务资料。 | 保留数据备份、失败不发布半成品索引、可诊断日志和明确的恢复入口。 |

## 审计限制与工作区状态

本结论仅归因代码阶段，不归因 OS 句柄来源。要识别真正来源，需要公司服务器侧在失败时采集可关联的进程/句柄或安全产品审计证据；本次不访问公司服务器，也不建议从现有日志推测责任方。

实际 EXE 验收另外发现：继承的组件裁剪器强制要求 staging 目录名，与新版本目录不兼容；完整版无需裁剪，改为直接完整校验。原 AfterInstall 抛异常还可能在显示错误后返回 0，不能作为完成依据。新入口使用 PrepareToInstall 返回失败，停止安装准备阶段，避免误报成功和更新错误启动入口。该事件的失败语义见 [Inno 官方文档](https://jrsoftware.org/ishelp/topic_scriptevents.htm)。
